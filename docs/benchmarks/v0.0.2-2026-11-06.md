# RayoPDF 0.0.2 on the harness, 2026-11-06

What changed since [0.0.1](v0-2026-11-05.md): tables (ruled, horizontal-rule-only and
high-confidence borderless; GFM, or HTML with spans), image files (`--images=DIR|none`, PNG with
RayoPDF's own deflate, DCT and JPX passed through), footnotes (`[^n]`), absolute heading levels,
running headers and footers of single pages, right-to-left lines (UAX #9), CJK fonts without
ToUnicode (Adobe CMap resources), and smaller fixes (URL link text, form blanks, inline images).

Same machine, harness, versions and data as [the baselines](baselines-2026-11-05.md) (olmOCR as
rescored there). RayoPDF ran as the harness's `cli` tool: `build/static/rayopdf` (GCC 13.3, `-O2`,
fully static, 2,027,120 bytes), `rayopdf --convert {in} {out}` with its default image output. All
numbers are reproduced here.

- On the synthetic corpus RayoPDF is now ahead of every tool, docling included, on every metric
  but tagged TEDS (0.845 against docling's 0.881).
- odl still trails liteparse on every metric. The diff study of the 30 documents where it loses
  most puts tables first by far (19,894 differing characters: false tables, pipe against HTML
  format, `colspan`), then reading order around tables and figures (4,196). Markup the odl ground
  truth never has costs too and stays: emphasis (1,375), image references (1,301, required by D6),
  curly quotes kept as the PDF has them (860).
- olmOCR: the born-digital mean passes the best text-layer tool; `long_tiny_text` and
  `multi_column` are 0.016 and 0.007 below 0.0.1 after false-table tuning.
- READoc holdout aggregates: github `text_eds` fell 0.909 → 0.873 and arxiv `seg_kt` 0.972 →
  0.950, while heading and table keys rose. Per-document outputs are not inspected (AGENTS.md
  rule 7); finding the cause needs an aggregate-only ablation (build variants with one feature
  off).

## Speed and memory

One pinned core (`--cpuset-cpus=3 --cpus=1`), the 200 odl PDFs and 6 multi-page synthetic PDFs,
a fresh process per document started from Python (about 1 ms of that is Python's).

| run | pages/s | ms/page median | ms/page p95 | cold start s | peak RSS MiB |
|---|---|---|---|---|---|
| 0.0.1 | 363.6 | 2.86 | 3.93 | 0.03 | 13.5 |
| 0.0.2, `--images=none` | 344.2 | 2.95 | 4.07 | 0.03 | 13.5 |
| 0.0.2, images written (default) | 153.8 | 3.34 | 16.24 | 0.04 | 188.3 |

- In process (release build, CPU 3, best of 3, odl, images off): 0.89 ms/page median and 1.99
  ms p95, against 0.78 and 1.86 for 0.0.1's code built the same way: +14.5 %, from table detection
  (about 71 µs/page) and the CJK and footnote stages.
- Writing images costs about 4.2 ms per odl document. Peak RSS comes from three odl pages with a
  10-megapixel RGB image and soft mask (4,653 × 2,334: 189 MB, 215 ms): the image is decoded,
  composited and encoded whole. Streaming it a row band at a time is open (M7).

## Robustness

- Full conversions with ASan + UBSan, images written: 2,784 PDFs (the synthetic corpus, odl, the
  1,269 olmOCR born-digital pages, the 1,000 SafeDocs files): 0 crashes, 0 hangs, 0 sanitizer
  reports (exit 0 for 2,780, 10 for 3, 11 for 1).
- Images alone (the image module's own sweep): 26,862 image XObjects, 0 Corrupt; 2,005
  Unsupported (CCITT 1,663, JBIG2 342).
- Every fuzz target ran at least 5 minutes clean during development; the long campaign is
  recorded separately.

## Known gaps

- Tables: odl TEDS 0.645 against 0.818 (worst: 088/089/090, 064, 149's one-column grid, 165's
  empty column); cells mixing code and wrapped text can split a table; wrapped lowercase cells in
  header-rule tables are rejected as prose (LibreOffice tagged TEDS).
- Images: CMYK JPEGs with Adobe's APP14 marker are passed through and look inverted outside PDF
  viewers; soft masks of DCT/JPX images are dropped; alt text waits for M6; large images are
  decoded whole.
- Footnotes continued on the next page are not joined; a multi-paragraph note becomes one
  paragraph.
- Right-to-left: no explicit embeddings, isolates or bracket pairs (UAX #9 X1–X10, N0); a
  paragraph mixing RTL and LTR lines can split.
- CJK: CIDs without Unicode in Adobe's tables and the predefined CMaps not generated (78-, Add-,
  Ext-, NWP, 83pv/90pv, GBT, GBK2K, ETHK/HKdl*, CNS-EUC, KSC-Johab, KSCpc, Adobe-KR) give no text.
- Garbage ToUnicode maps are not detected (algorithms §3.6); subset TrueType without a cmap and
  bare CID-keyed CFF with Identity ordering stay unmappable.
- Math stays Unicode text by design (D6): olmOCR `arxiv_math` 0, READoc `inline_eds` 0.001.
