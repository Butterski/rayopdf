# RayoPDF 0.0.12 on the harness, 2026-11-10

0.0.12 is the fourth performance round (research, method, every step and the rejected attempts:
[performance.md](../development/performance.md#fourth-round-research-first-then-ten-areas-at-once-2026-11-09);
the research behind it: [speed.md](../research/speed.md)). Output is byte-identical to
[0.0.11](v0.0.11-2026-11-09.md) in both math modes, so every quality number of 0.0.11 and
[0.0.10](v0.0.10-2026-11-09.md) stands: 6,331 comparisons over the synthetic corpus, odl, olmOCR
born-digital, SafeDocs and the scanned suite, 1,842 with `--math=latex`, 1,491 over READoc's 300
PDFs, olmOCR's old scans and the multiscript suite (Markdown, image files, exit codes and
`--report` records; the holdouts compared by bytes only).

What changed: the content lexer's loop runs inline in the interpreter with a fast path for
numbers and path operators; a text operator places its glyphs from one placement, the glyph box
in SSE2; page content decodes into one buffer; the inflate loop is 16 % shorter per byte and uses
BMI2 where the CPU has it; line building folds duplicates while it collects glyphs; ToUnicode
maps are judged in the pass that reads them (font loading halved on olmOCR `multi_column` and
`tables`); table detection and reading order lost a quadratic and a cubic step; the writer has a
one-pass path for plain blocks; release builds drop the unwinder and order their hot code
(`src/hot.ld`); `--batch` reads small inputs into a kept buffer and keeps its heap; and
`--convert` reads the pages of a document on up to four threads (`--workers=N`), with the same
output for every count.

`build/static/rayopdf`: GCC 13.3, `-O2`, static-pie, 3,315,776 bytes (0.0.11: 3,515,432).
Machine: AMD Ryzen 5 PRO 4650GE (6 cores, 12 threads), Linux 7.0, Docker.

## Speed

CPU 3 pinned, 0.0.11 and 0.0.12 interleaved, the machine otherwise idle. Warm: `--bench`, best of
3 per document. Fresh: a native `posix_spawn` timer, 11 runs a document after 2, 12 rounds with the
order of the binaries rotated.

| odl, 200 one-page PDFs, `--images=none` | 0.0.11 | 0.0.12 | release bar |
|---|---|---|---|
| warm, pages/s | 1,587 | **2,215** (+40 %) | ≥ 2,000 |
| warm, ms/page median / p95 | 0.492 / 1.056 | 0.370 / 0.686 | – |
| fresh process, ms a document, median | 1.065 | **0.885** (−16.9 %) | ≤ 1 |
| fresh process, p95 / mean | 1.80 / 1.23 | 1.45 / 1.01 | – |
| fresh process, page faults median | 161 | 150 | – |
| fresh process with images written, median | 1.359 | 1.110 | – |
| `--batch --workers=1`, task-clock for the 200 | 125.5 ms | 93.9 ms (−25 %) | – |

An empty static program takes 0.22 ms in the same timer. User instructions of a batch over each
set fell by 27 to 40 %: odl −29.5 %, SafeDocs (40 documents) −33.4 %, olmOCR `multi_column`
−39.8 %, `tables` −33.7 %, `arxiv_math` with `--math=latex` −31.1 %.

Documents of several pages (27 documents of 4 to 39 pages: 6 synthetic, 21 from SafeDocs), a
fresh `--convert --images=none` on four cores, median of 15 runs a document, summed: 0.0.11
262.8 ms; 0.0.12 with `--workers=1` 205.1 ms, with the default threads **147.4 ms (−44 %)**. No
document is slower with the default than with one thread: a thread starts only once the pages
read so far are worth it.

A JPEG 2000 page with its image written: 140.9 → 125.9 ms (100 pages of 40 scanned documents).

## Against other tools, each through its own command line

Every tool converts the same PDF as a fresh process, start to exit, through the command line its
package installs, in its own pinned image (versions: [evaluation.md](../development/evaluation.md#competitors)),
without network, output to a RAM disk; the median of N runs after warm-up runs (RayoPDF 40 after 3;
pdftotext, liteparse, edgeparse 20 after 2; opendataloader, markitdown 10 after 1; pymupdf 5 after
1; docling 3 after 1), timed by one native `posix_spawn` program inside each container. The tools
were measured on 2026-11-09 with the round's code of that evening; RayoPDF again on 2026-11-10
with 0.0.12. Reproduced numbers, this machine.

Four cores (thread variables 4): RayoPDF 8.8 ms for the 33 pages (pages on threads; the one-page

- This compares the time to a finished file, not identical output: pdftotext writes plain text,
  the others Markdown of different quality (the quality tables of [0.0.10](v0.0.10-2026-11-09.md)
  and the [baselines](baselines-2026-11-05.md)).
- A fresh process pays each tool's start: the Python tools import their packages (markitdown,
  pymupdf with its layout model, docling with its models), opendataloader starts a JVM. Inside
  one running process the gap is smaller: the baselines' warm figures are 4.9 ms a page for
  edgeparse and about 2 s a page for pymupdf and docling, against RayoPDF's 0.37 ms.
- Commands: `rayopdf --convert IN OUT.md --images=none`; `pdftotext -enc UTF-8`;
  `lit parse --format markdown --no-ocr --image-mode off`; `edgeparse -f markdown`;
  `opendataloader-pdf -f markdown --image-output off`; `markitdown -o`;
  `pymupdf.open(p).to_markdown()` in a three-line script; `docling convert --to md --no-ocr
  --device cpu --image-export-mode placeholder`.

## Robustness

- Tests pass in the release, ASan + UBSan, ThreadSanitizer and Windows (Wine) builds, 23 each
  (new: `layout_pages`, the pages of a document on 1, 2, 4 and 8 threads and on the default
  count); 0 warnings.
- `--workers=1` against 2, 4 and 8: 9,197 comparisons each, identical. ThreadSanitizer and ASan
  conversions of 399 documents (synthetic corpus and 200 SafeDocs files) with the default threads
  and with four: no report.
- Every changed parser of untrusted input was fuzzed for ten minutes per step, clean
  (`fuzz_layout_content`, `fuzz_layout_document`, `fuzz_pdf_document`, `fuzz_pdf_filters`,
  `fuzz_text_cmap`, `fuzz_text_repair`, `fuzz_text_program`, `fuzz_layout_tables`,
  `fuzz_layout_math`, `fuzz_image_jpx`, `fuzz_image_decode`). The fuzz targets convert on one
  thread; the shared-document mode is covered by the tests and the sanitizer runs.
